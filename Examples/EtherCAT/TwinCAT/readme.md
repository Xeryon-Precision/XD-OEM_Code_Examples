# TwinCAT (EtherCAT) — XD-OEM Motor Control

This folder contains a **TwinCAT 3** project (`XeryonDemoCommands`) that controls one or more **Xeryon EtherCAT drives** (XD-OEM) through their EtherCAT process image, wrapped in a reusable `XeryonDrive` function block plus a 4-axis demo program.

> [!NOTE]
> This project talks to the drive purely through its EtherCAT process image (`AT %I*` / `AT %Q*` mapped variables) — there is no serial/USB connection involved once the EtherCAT network is configured.

## Requirements

- TwinCAT 3 XAE (engineering environment, runs inside the Visual Studio shell)
- A TwinCAT 3 runtime target with an EtherCAT master (can be the same PC, e.g. `TwinCAT RT (x64)`)
- The Xeryon EtherCAT ESI file installed, and the XD-OEM/ drive(s) wired into the EtherCAT network
- *(Optional, for the scripting example)* Python 3 with [`pyads`](https://pypi.org/project/pyads/):

  ```bash
  pip install pyads
  ```

## The `XeryonDrive` Function Block

`XeryonDrive` ([`Demo/POUs/FB/XeryonDrive.TcPOU`](XeryonDemoCommands/Demo/POUs/FB/XeryonDrive.TcPOU)) wraps a single EtherCAT axis. Its `iDrive*` / `qDrive*` members are mapped directly onto the drive's process image (`AT %I*` / `AT %Q*`), so once you link one `XeryonDrive` instance's I/O to a slave in the System Manager, the rest of your PLC code only talks to the block's outputs and methods — never the raw process image.

**Outputs:**

| Output | Meaning |
|--------|---------|
| `ActPosition` | Actual position (from `iDriveActualPosition`) |
| `Done` / `Busy` | Command lifecycle flags |
| `HasError` / `Error` | Latched error flag and its `XeryonDriveError` code |
| `HasIndex` | Encoder index has been found |
| `MotorOn` | Amplifier/motor enabled |
| `LeftEndstop` / `RightEndstop` | Endstop states |

**Methods** (each returns an `XeryonDriveStatus`: `Waiting` while in progress, `Ready` on success, `Error` / `SoftError` on failure):

| Method | Purpose |
|--------|---------|
| `Enable(val)` | Enable/disable the amplifier |
| `Index(Direction, Velocity, Acceleration, Deceleration)` | Search for the encoder index |
| `MoveAbsolute(Position, Velocity, Acceleration, Deceleration)` | Move to an absolute position (requires an index first) |
| `MoveOpen(Direction)` | Open-loop jog in a direction until `Halt()` |
| `Scan(Direction, Velocity, Acceleration, Deceleration)` | Continuous scan until an endstop is hit |
| `Halt()` | Stop a `MoveOpen`/`Scan` in progress |
| `Stop()` | Stop the current motion |
| `Reset()` | Reset the drive and clear the latched error/index state |
| `ResetEncoder()` | Reset the encoder and clear the index state |
| `Write(setting, value)` | Write an arbitrary drive setting (4-character command + value) |
| `Init(settings)` | Sequentially applies an array of `XeryonDriveSetting {setting, value}` pairs, one per call, until all are written |

Internally, each method arms a small state machine (`state`, `new_command`, `command_start`/`command_irq`) that drives the `qCommand` / `qExecute` / `qDriveTargetPos` outputs and waits for `iDriveBusy` to toggle, so calling a method every PLC cycle is safe — it only issues the command once and reports `Ready` when the drive confirms completion.

## Shared Types (`Demo/DUTs/`)

| Type | Kind | Description |
|------|------|-------------|
| `XeryonDriveStatus` | Enum | `Waiting`, `Ready`, `Error`, `SoftError` — returned by every `XeryonDrive` method |
| `XeryonDriveError` | Enum | `NO_ERROR`, `LIMIT_HIT`, `NO_INDEX`, `THERMAL_1`, `THERMAL_2`, `ENCODER_ERROR`, `SAFETY_TIMEOUT`, `ERROR_LIMIT`, `ESTOP`, `POS_FAIL`, `DRIVE_DISABLED` |
| `XeryonDriveSetting` | Struct | `{ setting: STRING(5), value: DINT }` — one drive setting/value pair, used by `Init()` |

## `MAIN` — Demo Program

[`Demo/POUs/MAIN.TcPOU`](XeryonDemoCommands/Demo/POUs/MAIN.TcPOU) instantiates four `XeryonDrive` blocks (`Drive1`…`Drive4`) and runs `DRIVE_SETTINGS()` once at startup to push each drive's initial settings (via `GVL.Drive1Settings`…`Drive4Settings`) through `Init()`. Each drive then runs its own state machine, triggered by boolean inputs you can toggle from a watch window or the visualization:

- `driveNJogP` / `driveNJogN` — continuous scan in the positive/negative direction until released
- `driveNMoveP` / `driveNMoveN` — open-loop move until released (`Drive1` only)
- `driveNIndex` — search for the index
- `driveNMoveAbs` — cycle through a fixed set of `MoveAbsolute` test positions
- `driveNDpos` — move to `driveNTarget`
- `driveNInit` — re-run the settings `Init()` sequence
- `driveNEnable`, `driveNHalt`, `driveNStop`, `driveNReset`, `driveNResetEncoder` — direct passthrough to the matching method, checked every cycle

> [!NOTE]
> `MAIN` is demo/test code meant to exercise every `XeryonDrive` method, not a production control program. Use it as a reference for how to sequence calls to the function block, and replace the test state machines with your own application logic.

A `Visualization.TcVIS` under `Demo/VISUs/` provides a simple HMI to trigger these inputs and watch `ActPosition`, `Error`, and the endstop/status outputs live.

## Opening & Running the Project

1. Open `XeryonDemoCommands/XeryonDemoCommands.sln` in TwinCAT XAE.
2. In the System Manager (`XeryonDemo.tsproj`), scan or configure your EtherCAT master and link the discovered XD-OEM slave(s) to the `Drive1`…`Drive4` instances' `iDrive*`/`qDrive*` variables (only as many drives as you have need `Init`/enabling — leave the rest disconnected).
3. Build the PLC project and activate the configuration (Run mode).
4. Toggle the `driveN...` inputs from a watch window or `Visualization.TcVIS` to exercise indexing, scanning, and absolute moves.

> [!IMPORTANT]
> `DRIVE_SETTINGS.TcPOU` only defines a `4PHS` setting for each drive by default — the rest of a typical settings block (limits, encoder config, PID gains, etc., visible commented-out in the source) is left inactive. Uncomment and adjust the settings your setup actually needs before relying on `Init()` for production configuration.

## Scripting via ADS (`Scripts/Example.py`)

[`Scripts/Example.py`](XeryonDemoCommands/Scripts/Example.py) shows an alternative to writing PLC code: it uses `pyads` to read/write the same `MAIN.Drive1.*` symbols directly over ADS from a Python script (index search, then a negative and a positive scan). This is useful for scripting test sequences or integrating the PLC with external tooling without touching the TwinCAT project itself. Update `net_id` and `port` to match your target system before running it.

## Safety Notes

- Always run this project with the motor(s) mechanically free to move — the demo state machines start motion as soon as their trigger input is set.
- `HasError` latches until `Reset()` (or `Enable()` with `val = TRUE`) is called — check `Error` before assuming a stalled command is a bug.
- Only wire up and enable as many `Drive1`…`Drive4` instances as you have physical axes connected; leaving an instance's I/O unlinked while still calling `Enable`/`Init` on it will not behave meaningfully.
